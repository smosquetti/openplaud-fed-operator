openplaud-fed-operator

React + Next.js

An XMPP powered chat call center, an operator should first log in with their XMPP credentials then after authenticated they have access to the list of Operator Groups they are part of and should subscribe the Groups respective persistent MUC rooms.

The login:

The openlaud-srv-admin has an endpoint for Operators to login/authenticate, this validates if the Operator has the right to access the chat interface and take "calls".

Ejabberd and XMPP:

The chat call center should connect the Operator with the ejabberd server using the Strophe.js library over Websocket (try to avoid BOSH), the openlaud-srv-admin is only for authentication and management.

The interface:

There's vertical panel on the left side of the page, this panel shows each MUC room the Operator is receiving messages from, each MUC is represented by a card with the title/header being the name of the Group (if it is a persistent MUC room based on an Operator Group) or the name (nick in ejabberd) of the user who created the Tempo Room, below the title the lastest message sent within the room should be shown. When clicking on the card a Chat windows should apear to the right of this vertical panel, the entire conversation history should be shown and the Operator can choose to accept the "call" by joining it, when joining the chat all other Operators should be removed from the MUC room so the Operator can have a 1:1 conversation with the user who created the temporary MUC room.

The Temporary MUC room should be titled after the User's nick (the User is the sole occupant with a 'member' affiliation) or the MUC's title, all the Operators are configured with an 'admin' affiliation. (the Temporary MUC room is idenfitied on Ejabbed by its name, created from the combination of the user's XMPP username (localpart) with is an auto-generated UUID and an underscore '_' and the Operator Group UUID example: c04582c4-cf45-4191-a8ac-6d9b0b041c79_c7fc5856-51f2-47d3-a0d2-ef26a6692200 snake_case style. The Operator may use the last part, the groupId, after the underscore to get the list of Operators assigned to the Group so a future chat transfer is possible.)

An Operator can have multiple chat rooms open at any given time and should be able to drag the chat window around the page as well as minimize it to the bottom of the page to avoid too many distracting chat windows populating the page.

Operators are subscribed to Temporary MUC room upon creation, the Operators are selected based on the Group they belong to.

Subscribing to a Multi-User Chat (MUC) room in ejabberd (via the MucSub / MUC/Sub extension) allows a user to receive group messages and room events directly to their Jabber ID (JID) as a PubSub node, without needing to "join" the room or send online presence stanzas.

What Subscribing Does

• Receive Messages Without Presence: You get all chat messages and room notifications routed to your JID without having to show up as an active, online participant in the room's occupant list.
• PubSub Architecture: It exposes the MUC room like a Publish-Subscribe (PubSub) channel. When messages are published to the room, the server delivers them to all subscribed JIDs.

POST /api/v1/chatroom endpoint does not require authentication
GET /api/v1/groups endpoint does not require authentication

Those two endpoints are public for the Customer's end to consume.

  Additional information:

  In ejabberd 26, the intersection of MUC/Sub, members-only rooms, and non-occupant Admins contains a strict, counter-intuitive routing trap.

   The Problem: Admin ≠ Member in ejabberd 26 routing

   When a room is marked members-only, ejabberd 26 triggers a hard intercept hook (check_access) inside mod_muc.
   • The Trap: When a standard occupant sends a message, ejabberd loops over the active subscription list. For every recipient, it evaluates whether they have permission to see the content of that members-only room.
   • The Check: The routing engine evaluates if the target JID has the specific authorization state of member.
   • The Failure: Even though an admin or owner affiliation holds a higher general rank than a member, ejabberd's literal validation check looks for the member attribute specifically in the room's access list. If you are an admin but your JID is missing from the explicit room member list, the packet is silently dropped by the privacy check before it hits the delivery queue.

   IMPORTANT: At this moment the API is setting the Operator's affiliation as 'admin' I've kept this behaviour because other changes are in place and I want to make sure which one actually fixes the issue.
   If the test fails the next step will be to change the API to set the Operator's affiliation to 'member' during the MUC creation process.

### XMPP / Strophe learnings (verified live against ejabberd 26.9 — do NOT revisit)
- MucSub subscribe CONFIRMED: `<iq to='room@conference' type='set'><subscribe xmlns='urn:xmpp:
  mucsub:0' nick='...'/></iq>` — type='get' is REJECTED; the `nick` attribute is required.
- Subscription list: `<iq type='get' to='room@conference'><subscriptions xmlns='urn:xmpp:mucsub:0'/></iq>`
  → `<subscription jid='...' nick='...'/>` items (used for transfer candidates; /groups/{id}/operators
  is admin-gated so NOT usable).
- MucSub delivery wrapper: outer `<message to='BARE'>` → `<event pubsub#event>` →
  `<items node='urn:xmpp:mucsub:nodes:messages'>` → `<item>` → inner
  `<message from='room@conference/Nick' type='groupchat'><body>..</body></message>`.
- Room naming: group = `room@conference` (service EXACTLY "conference"); temp = `<userLocalPart>_
  <groupUUID>`; part AFTER first '_' = groupId; part BEFORE = customer localpart (excluded from
  transfer candidates; MAM partner for temp calls).
- MUC join: `$pres({to:'room@conference/Nick'}).c('x',{xmlns:'http://jabber.org/protocol/muc'})`;
  leave = presence type='unavailable'; send = `$msg({to:room,type:'groupchat'})`. Initial `$pres()`
  after connect is REQUIRED for MucSub routing. Non-occupant group send is dropped → auto-join on
  first send (pendingBody + 3s fallback).
- MAM LIMITATION (locked): the custom mod_mam build returns ONLY
  `<fin complete='true'><set count first last/></fin>` — NEVER stanza content. A working query has
  NO date fields. App strategy: client-side per-room accumulation (in-memory +
  sessionStorage 'openplaud.operator.history', cap 500/room) + best-effort MAM count banner.
  Do NOT expect MAM to return items.
- strophe.js 5.0.0 (TS rewrite) API facts:
  - Root exports: Builder, $build, $iq, $msg, $pres, Strophe, Stanza, stx, toStanza, Request,
    StreamManagement — **Connection is NOT exported from the root**.
  - `Strophe` = `declare const Strophe: StropheType` (value-only const); `StropheType.Connection:
    typeof Connection` (static, non-optional). Instance type =
    `InstanceType<NonNullable<typeof Strophe['Connection']>>`.
  - `ConnectCallback = (status: number, condition: string|null, elem?: Element) => void`;
    `addHandler(handler:(stanza:Element)=>boolean, ns, name, type, id, from, options)`;
    `sendIQ(stanza, cb?, errback?, timeout?)`.
  - Status codes: ERROR=0, CONNECTING=1, CONNFAIL=2, AUTHFAIL=4, CONNECTED=5, DISCONNECTED=6,
    CONNTIMEOUT=10, RECONNECTING=13.
- Strophe SSR bundling: Turbopack statically analyzes even dynamic `import('./client')` — strophe
  resolves to the Node build (strophe.node.esm.js) needing optional peers; fixed by
  `npm install ws @xmldom/xmldom saxes` (devDeps). Do not remove.
- @xmldom has no querySelectorAll — use childNodes walkers (see lib/xmpp/client.ts
  childByName/childrenByName/textOf helpers).
